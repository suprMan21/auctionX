## 0. Counter-rule security review (gate before any build)

### How taps work today (read 2026-10-29)

- `nfc_tags.sun_counter` is one high-water mark per chip (`services/nfc/tapResolver.ts`).
- Every accepted tap (public `/nfc/tap`, `/nfc/scan`, claim, transfer complete) needs MAC ok **and**
  `counter > sun_counter`, then burns it with `update … .lt('sun_counter', n)`. Zero rows = `replay_detected`.
- A SUN URL stays cryptographically valid forever (static file key, no challenge). The high-water mark is
  the only thing that makes it single-use.
- Encode-time counter is not stored separately. `sun_counter` is updated by every tap.

### Why sealing breaks this

The app captures tap 1 (c1) and tap 2 (c2) offline and syncs later. If any other tap reaches the server first
(the creator checks the item with the phone camera, a fan taps it at the venue), it burns c3 > c2.
The seal sync then has c1, c2 < `sun_counter` and today's rule rejects it as a replay.

### Options

| | Rule | Creator sees a delay? | Risk |
|---|---|---|---|
| **A (recommended)** | Counter ledger: every accepted counter is stored (`unique(tag_id, counter)`). **Seal path only** accepts c1 < c2 that are MAC-valid, above the chip's seal baseline, and not in the ledger. Public / claim / transfer keep the strict high-water rule unchanged. | No | Someone holding an undelivered URL from a loose seal could use it, but only through the seal path, which needs a Creator account + `seal` step-up + an unclaimed chip. Same exposure as today's first-tap claim. |
| B | Strict: if another tap beat the sync, the seal fails and the creator redoes (labelled "seal applied before recording"). | Yes, sometimes | None new, but breaks Boss's "user should not notice the delay". |

### Rule A in detail

1. **Ledger** `nfc_counter_ledger (tag_id, counter, source, accepted_at)`, unique `(tag_id, counter)`. Every
   existing burn also inserts (same transaction, via one SECURITY DEFINER RPC, REVOKE from PUBLIC/anon/authenticated).
2. **Seal baseline** = `sun_counter` when the ledger goes live for that chip (everything at or below it is treated as
   spent; older taps were never recorded). Stored on the chip row, write-once.
3. **Seal commit** accepts only if: both MACs ok, same chip (serial + UID), `baseline < c1 < c2`, neither in the
   ledger, chip has no owner / origin claim / earlier seal, caller is a Creator with a fresh `seal` step-up bound to
   the chip. One transaction: insert both counters, create the seal record, `sun_counter = greatest(sun_counter, c2)`.
4. **Gap** `c2 - c1 - 1` stored. 0 = nothing read the chip during the video. See decision D2.
5. **Order by counter**, never arrival time. Any ledger counter between c1 and c2 also counts as a gap.
6. **Collectors never get out-of-order acceptance** and never an optimistic green offline (Locked hard rule).
7. Live SQL checks: replay of c1 refused, c2 ≤ c1 refused, counter ≤ baseline refused, ledger hit refused,
   public tap after seal still strict, two racing seal commits → one wins.

## Phases

- **Ph A — backend** (migration + live SQL): ledger + baseline, `seal` step-up action (passkey or authenticator code,
  never a backup code; 24 h cool-off applies), `POST /seals` commit (two taps + video hash + device time + optional
  server-signed time from tap 1), `seal_sessions` linking tap 1 and tap 2, seal record states
  `pending_video → in_review → live`, private bucket for videos (no public read).
- **Ph B — app sealing flow**: prep screen (Brand Voice draft in the Ideas DB row; adds "not on metal", "press firmly",
  "turn off music", "don't ship for 24 h"), practice run, tap 1 (same-seal check on `sn`), 3-2-1, record (warn 1:45,
  void 2:00), tap 2 stops, review → Seal it / Redo, `withStepUp('seal', chipId, …)`, offline queue, "Sealed" (still,
  Owned style) + quiet Syncing, Verified only after the server confirms.
- **Ph C — video upload + review**: resumable upload to the private bucket, hash must match the commitment, admin
  review queue (2–3 clicks rule), tap page shows "Video in review" / "Video unavailable" / "Video removed by the creator".
- **Ph D — share + device tests**: Share link / picture (reuses `/s/<code>` and seal pictures), Instagram Stories
  (needs a Facebook App ID), real iPhone test on an existing chip (conserve chips). Android when a device exists.

## Decisions for Boss

**Boss 2026-10-29:** D1 = A (ledger), D2 = reject + Redo, D3 = any Creator with an unclaimed chip. D4 = defer App Attest / Play Integrity to S-SEC1.

- **D1** counter rule: A (ledger, recommended) or B (strict + redo).
- **D2** a gap between tap 1 and tap 2: reject the take (Redo), or accept and flag it for staff.
  Recommend **reject**: the gap is the whole point of the bracket, and the seal is already on, so Redo is a re-tap pair
  labelled "seal applied before recording".
- **D3** who may seal until the tag store exists: any Creator with an unclaimed chip (recommended), or staff assign
  chips to a creator first.
- **D4** App Attest / Play Integrity signature on the commitment: defer to S-SEC1 (recommended; the step-up already
  binds the commit to a person) or build in Ph A.
