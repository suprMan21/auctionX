# S-NFC3-FE Plan: Token Lifecycle Frontend (+ the backend reads it needs)

**Date:** 2026-10-03 · **Branch:** `feature/s-nfc3-fe` (from `dev` @ `6479f7d`) · **Status:** awaiting Boss approval

## Objective

Give the token lifecycle API a working web front end. One tap of a chip opens a page that proves it is
genuine and lets the right person claim it or take a transfer. Owners manage their tokens from My Tokens.
Ship it to staging so the stale 2026-05-30 marketplace build is finally replaced.

## Decisions taken at planning (Boss, 2026-10-03)

| # | Question | Answer |
|---|---|---|
| D1 | A tap is burned by the verify page, yet claim and transfer-complete need a fresh one | **Tap session.** `POST /nfc/tap` verifies and burns the tap, then returns a short-lived single-use token that `/claim` and `/transfer/:id/complete` accept |
| D2 | Scope (needs new backend reads) | **Two phases**, one session each, each with its own verification doc |
| D3 | Marketplace-era NFC pages | **Park behind `VITE_FEATURE_MARKETPLACE`**, strip `aesKey`, `/nfc` → My Tokens |

## Why backend work is in a "frontend" session

Recon on 2026-10-03 found the S-NFC3 API is write-only from a UI's point of view:

- **No endpoints for:**
  - my tokens
  - transfers addressed to me
  - transfer status (the webhook is the only writer of `COMPLETED`, so the UI has to poll)
  - receipt download (`openReceipt()` exists at `backend/src/lib/ownership/ownershipProof.ts:228` but no route calls it)
- **`youOwnThis` is always false** on `GET /ownership/:id`, because there is no optional-auth middleware.
- **The tap URL is `/verify/:tokenName?picc_data&cmac`, but nothing uses it correctly.**
  - The frontend page there calls the marketplace-era API.
  - `/claim` needs a `tagUid`, which the URL never carries because the UID is encrypted inside `picc_data`.
  - The only way to learn the UID today is `/nfc/scan`, which burns the counter, so the claim that follows always fails `replay_detected`.

## Phase 1: Tap, verify, claim, My Tokens, deploy

### Database (1 migration)

`supabase/migrations/20261003000001_nfc_tap_sessions.sql` (idempotent DDL per lesson):

```sql
CREATE TABLE IF NOT EXISTS public.nfc_tap_sessions (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tag_id        uuid NOT NULL REFERENCES public.nfc_tags(id) ON DELETE CASCADE,
  token_hash    text NOT NULL UNIQUE,          -- SHA-256 of the bearer token; raw token never stored
  counter_value integer NOT NULL,              -- SUN counter that was burned to mint this session
  expires_at    timestamptz NOT NULL,          -- now() + 10 min
  consumed_at   timestamptz,
  consumed_by   uuid REFERENCES public.users(id),
  consumed_for  text CHECK (consumed_for IN ('claim','transfer_complete')),
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS nfc_tap_sessions_tag_idx ON public.nfc_tap_sessions(tag_id);
ALTER TABLE public.nfc_tap_sessions ENABLE ROW LEVEL SECURITY;
REVOKE ALL ON public.nfc_tap_sessions FROM anon, authenticated;   -- service role only; no policies
```

Single use is enforced in one conditional `UPDATE … SET consumed_at = now() WHERE token_hash = $1 AND
consumed_at IS NULL AND expires_at > now() RETURNING tag_id`. It returns zero rows on reuse or expiry.
No enum changes. Types are regenerated into **both** `frontend/` and `backend/` afterwards.

### Backend endpoints

All responses use `{ success, data, error }`. Static routes are registered in `tagManagementRoutes`, which is
mounted before `nfcRoutes`' `GET /:tagId` catch-all. No request body carries `ownershipId`/`receipt`
keys (the probe detector logs them).

| Method + path (`/api/v1`) | Auth | Purpose |
|---|---|---|
| `POST /nfc/tap` | public (optional auth), 30/min | Body `{ sunMessage }`. Runs the existing S-NFC3.5 SUN verify and burns the counter. Returns `{ valid, reason?, provenance, tapSession?: { token, expiresAt }, viewer? }`. `tapSession` is issued only when the token is `ENROLLED` (claimable) or `ACTIVE` (transfer target). `viewer` is present when signed in: `{ youOwnThis, canClaim, pendingTransferId? }` |
| `POST /nfc/claim` | user + 2FA gate | **Also** accepts `{ tapSession }` (Zod `union` with the existing `{ tagUid, sunMessage }`, both `.strict()`). The session's `tag_id` replaces the UID lookup |
| `POST /nfc/transfer/:id/complete` | recipient + 2FA gate | Same: accepts `{ tapSession }`. The session's `tag_id` must equal the transfer's tag |
| `GET /nfc/mine` | user | Tokens where I am the current owner: tag id + name, lifecycle, claim date, current Ownership ID, disclosure, any outgoing `PENDING` transfer |
| `GET /nfc/transfers/incoming` | user | `PENDING` transfers where `to_user_id = me` **or** `to_email = my confirmed email` |
| `GET /nfc/transfer/:id` | sender or recipient only | Status + amounts, for polling after payment. Registered after `/transfer/initiate` |
| `GET /nfc/:tagId/receipt` | current owner only | `{ ownershipId, tagRef, saltHex, issuedAt }` via `openReceipt()`. `Cache-Control: no-store`. Logged as a security event |
| `GET /ownership/:ownershipId` | **optional auth** (new middleware) | Unchanged contract; `youOwnThis` now works |

**New middleware:** `optionalAuth` in `backend/src/middleware/auth.ts` sets `req.user` when a valid bearer
token is present and never rejects.

**Every query runs on the service client and is filtered manually by user id** (the service client
bypasses RLS). Ownership and recipient checks are done in SQL, never trusted from the client.

### Frontend (Phase 1)

| Component / page | Route | Purpose |
|---|---|---|
| `TokenVerifyPage` | `/verify/:tokenName` | Reads `picc_data`/`cmac` (and short `e`/`c`). POSTs `/nfc/tap`, saves the result in `sessionStorage` keyed by URL (so a refresh doesn't hit `replay_detected`), then strips the SUN params with `history.replaceState`. Shows genuine / not genuine, status (`ACTIVE`, `RELEASED`, `RETIRED`, `SUSPENDED` as plain language), disclosed origin fields, the buyer warning ("don't pay until the seller starts a transfer to you"), and the next action: **Claim** / **Accept transfer** / **You own this**. With no SUN params it says "Tap the tag to verify" (or falls back to the legacy `VerificationPage` when the marketplace flag is on) |
| `ClaimTokenFlow` | modal / step on verify page | Sign-in gate (return to the same verify URL after login) → confirm → `POST /claim { tapSession }` → success showing the Ownership ID. Handles `already_claimed`, `token_released`/`retired`, the `2fa_required` 403 (explains 2FA is coming; flag is off on staging) and an expired tap session ("Tap the tag again") |
| `MyTokensPage` | `/tokens` (protected); `/nfc` redirects here | Cards from `GET /nfc/mine` + an "Incoming transfers" section from `/nfc/transfers/incoming`. Ph1 detail is read-only |
| `TokenDetailPage` (read-only shell) | `/tokens/:tagId` | Status, origin, Ownership ID (copy). Action buttons land in Ph2 |
| `OwnershipLookupPage` | `/ownership/:ownershipId` | Public resolver; current → provenance + "You own this"; stale → "This Ownership ID is no longer current" and nothing else |
| `tokenApi.ts` | `frontend/src/features/tokens/api/` | Typed client with a shared envelope parser that keeps `code`/`reason` (today's `api.ts` drops them). Zod schemas for every response |
| `useTokenStore` | `frontend/src/features/tokens/store/` | Zustand: tokens, incoming transfers, last tap result |

## Phase 2: Transfer, release, disclosure, receipt (frontend only)

All endpoints exist after Phase 1.

| Feature | Where | Notes |
|---|---|---|
| Initiate transfer | `TokenDetailPage` → `TransferInitiateDialog` | Sale or gift; recipient by email (user search is out of scope, so email only); fee payer (recipient default / I'll pay). Shows the $2.50 list price |
| Cancel transfer | `TokenDetailPage` | Sender only, while `PENDING` |
| Accept + pay | verify page (tap) and incoming-transfer card → `TransferCompleteFlow` | `POST /transfer/:id/complete { tapSession }` → Stripe `Elements` with the returned `clientSecret` → `stripe.confirmPayment` → "Processing" with polling `GET /transfer/:id` until `COMPLETED` (or timeout, with a "we'll email you" message). Shows `chargedAmount`/`chargedCurrency` from the response, never a hard-coded $2.50. Reuses the appearance config from `components/PaymentForm.tsx` |
| Release | `ReleaseTokenDialog` | Irreversible warning → second confirmation → type `RELEASE` → `POST /release`. Disabled with an explanation while a transfer is pending |
| Disclosure | `DisclosureSettings` | Four toggles (`origin_video`, `creator_name`, `claim_date`, `location`) with a live preview of what the verify page shows |
| Ownership + Receipt | `OwnershipPanel` | Copy the ID, link to `/ownership/:id`, download the Receipt as JSON (generated client-side from the receipt endpoint) |
