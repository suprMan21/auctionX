# S-SEAL1 Ph2 — Seal spec, public seal page, preview + share images — build plan

Backlog row S-SEAL1 (Notion 4073baf6…e0bd0e0, AC 1, 2, 3, 5, 6, 8, 9, 10), DR-22 v1.2, Ph1 report `docs/S_SEAL1_PH1_VERIFICATION.md`.
Branch `feature/s-seal1-ph2`, worktree `.claude/worktrees/s-seal1-ph2`, off local `dev` `daa72cd`.
Runs in parallel with S-MOB1 Phase C (app only). This plan touches no file under `mobile/` and does not edit
`frontend/public/.well-known/*` (Phase C passkeys depend on them).

## Objective

Each seal gets its own stored design (the "seal spec": code + colour pair + a pattern seeded from its code), drawn the same
way on the website and by the server. Anyone with a link can open a public seal page `/s/<seal code>` with a proper link
preview, and an owner can share the link or a share picture of their seal.

## Split (two sessions)

- **Ph2a — seal spec + pattern v1** (~1.5 days): migration, spec builder, `SealBadge` draws the spec, backfill, pattern preview for Boss.
- **Ph2b — seal page + images + share** (~2.5–3 days): server SVG template + renderer, `/s/<code>` HTML, preview image,
  share image, Share buttons, CloudFront behaviour, live check.

Out of scope: Flutter seal widget (after Phase C, S-MOB1 tree), creator colour choice (S-SEAL2), MP4 / og:video (S3),
tilt shine, public domain hosting of `/s/` (moves with the ECS cutover / S-LAUNCH1).

## Locked design: pattern v1 (Boss 2026-10-28)

Chosen from moving previews (variants A to F, then F2 tuned to GPKD-67QP). Reference page:
`docs/design/seal-pattern-v1-motion-preview.html`; stills in `projectClaude/design-assets/seal-pattern-v1/`.

- **Pattern:** two hypotrochoid rings inside the badge's inner circle (radius 29 outer, 17 inner), white, stroke 0.35,
  opacity 0.20 outer / 0.14 inner. Shapes limited to 13, 14 or 16 petals with 3 loops (r/R 0.18 to 0.24, one entry
  per curve); loop depth d/r 1.65 to 1.9 outer, 1.15 to 1.35 inner; angle from the seed. 28 points per petal.
  Built by `backend/src/lib/seal/sealSpec.ts` (6 unit tests); specs about 6 KB.
- **Motion: Shimmer (Boss 2026-10-28, replaces the electrons). Verified only (the 90 s after a tap):** words turn every
  12 s; outer ring turns the other way every 48 s, inner with the words every 30 s; ring lines are **holographic**
  (cyan → violet → pink → gold → mint, gradient turns every 8 s; opacity .45 / .35); a faint rainbow **sheen** over the
  badge (opacity .16, screen blend, turns every 14 s); a soft rainbow **glint** sweeps across at 25° (3 s), first 1 s after
  the seal appears, then every 30 s, lighting the sheen (.55) and the ring lines (stroke .7). No dots, no chasing
  segments. Glow 3.0 s unchanged. Pattern shape unchanged (round, v1), so stored specs are unchanged.
  Options reviewed: `docs/design/seal-motion-options.html` (chosen: "Shimmer · Round").
- **Still everywhere else** (Sealed / My Seals / `/s/` / share images: white rings, no sheen); **Reduce Motion**: holographic look stays, nothing moves.
- Rejected: atom with tilted orbits (C, D, E), light streaks (B), spiky first drafts, sparser 6 to 10 petal rings (F3);
  2026-10-28: electrons, chasing segments, split lines, spark, faceted / hexagon / star-line shapes.
- Build note: the preview uses SMIL `animateMotion` for the electrons. In the app use CSS `offset-path` (or SMIL
  paused from JS) so Reduce Motion and the 90 s end can stop them; Flutter draws the same paths later.

## Ph2a — seal spec + pattern v1

### Database — `20261028000004_seal_spec.sql` (additive, idempotent)

- `nfc_tags.seal_spec JSONB` (nullable), CHECK `seal_spec ? 'v' AND seal_spec ? 'code'`.
- `nfc_tags.seal_design_version_id UUID` (nullable, no FK until S-SEAL2 creates its table).
- Write-once: extend `nfc_tags_identity_write_once` so `seal_spec` cannot change or be cleared once set (same pattern as
  `seal_code`). A new pattern version later means a new column value only for tags without one (or a deliberate migration).
- No grants change: anon still reads no `nfc_tags` row.
- Live SQL `supabase/tests/seal_spec_live.sql` (BEGIN … ROLLBACK): write-once (change + clear refused), retired rows can be
  given a spec once, anon / authenticated cannot read it. Dry run before `db push`.

### Spec (built by the backend, stored per tag)

```json
{ "v": 1, "code": "WAV4F6TT", "colors": "am-default",
  "pattern": { "kind": "hypotrochoid", "version": 1, "paths": ["M…", "M…"] } }
```

- `backend/src/lib/seal/sealSpec.ts`: `buildSealSpec(sealCode)` — pure. Seed = SHA-256(`"am-seal-v1|" + code`); seed bytes pick
  2–3 hypotrochoid rosettes (R, r, d from small allowed ranges so every result looks good), sampled and written as SVG path
  strings fitted to the 120×120 badge, rounded to 2 decimals. Decoration only, not a security feature.
- `colors` is a key into AM's pair list (`lib/seal/colorPairs.ts`); Ph2 has one pair, `am-default` (today's purple → blue).
  S-SEAL2 adds the creator's choice.
- Stored when missing: `ensureSealSpec(tag)` writes it the first time a tag with a seal code is read (tap, My Seals, `/s/`),
  and `scripts/backfill-seal-specs.ts` fills every existing tag once (Boss runs it, or Claude hands over the SQL).
  New enrolments get it at enroll.
- Tests: deterministic (same code → same spec), different codes → different paths, every path inside the badge, size
  budget (spec < 10 KB; samples 5–9 KB), version recorded.

### Backend reads

- Valid tap response and `GET /nfc/mine` add `sealSpec` (only `v`, `colors`, `pattern`; the code is already `sealCode`).
  No-private-fields tests extended (keys pinned).

### Web

- `SealBadge` takes an optional `spec`; draws its pattern paths and colour pair. Without a spec (older backend, homepage
  demo) it draws exactly what it draws today, so the homepage is unchanged (`HomePage.test.tsx`, `publicSite.test.ts`).
- Tap page, `OwnedSeal`, token detail pass the spec.
- Geometry constants (scallop, AM mark, ring path) move to `frontend/src/components/seal/geometry.ts`; the backend copy is
  `backend/src/lib/seal/geometry.ts`. A test on each side hashes the constants against one pinned value so they cannot drift.

## Ph2b — seal page, images, share

### Server seal drawing

- `backend/src/lib/seal/sealSvg.ts`: the same seal as an SVG string from the spec (state `sealed` only, still ring).
- Renderer: `@resvg/resvg-js` (prebuilt linux-x64 binary). Fonts bundled in `backend/assets/fonts/` (Plus Jakarta Sans 800,
  IBM Plex Mono 600/700, OFL licences). Add `sharp` only if a PNG misses the size budget. `qrcode` for the QR (SVG output).
- Build check before any push: `npm ci` + render test on linux x64 (Docker `node:22`), because App Runner builds from source
  and a broken native module would take staging down while Phase C is testing.

### Routes

| Method | Path | Auth | New? | Notes |
|---|---|---|---|---|
| GET | `/s/:code` | public | new | Server HTML. Accepts any case / hyphen / Crockford look-alikes (I, L → 1, O → 0); redirects 301 to `/s/XXXX-XXXX`. Rate limited per IP. |
| GET | `/s/:code` HTML cache | — | — | `Cache-Control: public, max-age=60, stale-if-error=86400`; CloudFront Origin Shield on. |
| GET | `/seal-img/<code>/preview-v1.png` | public (S3 via CloudFront) | new | 1200×630 PNG < 300 KB: Sealed seal, code, "Picture only · tap the seal to check", link. Drawn when the seal gets its spec (enroll, backfill), stored in S3, `Cache-Control: public, max-age=86400`. Deleted when the seal is released, retired or put on hold; the page then points at `/seal-img/inactive-v1.png`. |
| GET | `/api/v1/nfc/:tagId/share-image` | owner | new | 1080×1920 PNG with QR + link + band. Current-owner check on the server (an earlier owner loses access after transfer). `no-store`. No step-up (DR-22: sharing needs none). |

- `/s/` and the preview image are mounted before the `/api/v1` version gate and outside the API CORS (plain GET pages).
- Page content: Cinema look, inline CSS, **no JavaScript**, strict CSP (`default-src 'none'; img-src 'self'; style-src 'unsafe-inline'`
  or a hash), `X-Robots-Tag: noindex` on staging. Shows the still Sealed seal, the code, the reliance sentence (P5), and only
  what the verify page shows for that seal, read from `public_tag_provenance` (follows the owner's disclosure toggles:
  creator name, claim date, location, origin video link). Never owner, prior owners, tagId, serial, UID, chip name, Ownership ID.
- Head: `og:title`, `og:description`, `og:image` (absolute, versioned), `og:image:width/height`, `twitter:card summary_large_image`,
  canonical URL. Staging base URL from `PUBLIC_SEAL_BASE_URL`.
- Inactive / unknown → P3 page, HTTP 404, generic preview image.

### Web (owners)

- Token detail + My Seals card: **Share link** (`navigator.share({ url })`, else copy with a "Link copied" status) and
  **Share image** (fetch the PNG, `navigator.share({ files })`, else download). Two buttons, never file + link together.
  Shown only to the current owner of an active seal.

### S3 + CloudFront (Boss)

- New private bucket `am-seal-images-staging` (us-east-2, OAC, no public access); backend role `am-backend-staging-instance`
  gets `s3:PutObject` / `s3:DeleteObject` on it only. Share images (1080×1920) live in the same bucket under a key the
  owner endpoint reads; they are never served publicly.
- Staging distribution: behaviour `/seal-img/*` → the bucket (OAC).

- Staging distribution: behaviour `/s/*` → backend origin (App Runner URL), caching policy honouring origin headers,
  no cookies / no query string forwarded. Steps written in the verification doc.

## Ph2b infra check (2026-10-29, Boss set up S3 + CloudFront)

- Bucket `am-seal-images-staging` (private, SSE-S3, OAC `am-seal-images-staging-oac`); bucket policy lets CloudFront read
  `seal-img/*` only; backend role inline policy `SealImagesStaging` (Put/Delete on the bucket, Get on `share/*`).
- Behaviours `/s/*` → App Runner origin (Origin Shield us-east-2, cache policy `am-seal-page-60s`: 0/60/86400, no
  headers / query / cookies, no origin request policy) and `/seal-img/*` → bucket (CachingOptimized).
- Probe: `/seal-img/nothing.png` → raw S3 `403` (routing OK, 403 not rewritten). `/s/WAV4-F6TT` → `200` SPA
  `index.html` with `x-cache: Error from cloudfront`: the backend's 404 was **rewritten by the distribution's custom
  error response (404 → /index.html 200)**, which applies to every behaviour.
- **Build rule for Ph2b:** `/s/` never answers 404. The shared "can't show this seal" page returns **200** with
  `<meta name="robots" content="noindex">` + `X-Robots-Tag: noindex` (and `Cache-Control` 60 s). Missing images come back
  as S3 403 (not rewritten). Re-probe once the route exists: expect `x-cache: Miss/Hit from cloudfront`, `x-powered-by`
  absent or the page's own headers.
